01 · Daily 5-Step Loop

Urutan sederhana untuk setiap pekerjaan coding di terminal Claude Code. Hindari langsung meminta Claude mengedit kode sebelum memahami dan merencanakan tugas.

01

ORIENT — Pahami Project & Context

Buka repository yang benar. Baca README/CLAUDE.md dan cek status Git tanpa mengedit file.

Orient yourself in this repository. Read CLAUDE.md, relevant entry points, project structure, and git status. Do not edit any files. Summarize architecture, canonical patterns, test commands, and key risks.
02

PLAN — Buat Rencana & Acceptance Criteria

Tekan Shift+Tab untuk masuk Plan Mode. Untuk perubahan multi-file atau berisiko, minta rencana dan review dulu — tidak ada file yang diedit selama mode ini aktif.

Enter plan mode for [TASK]. Formulate a minimal implementation plan. List exact files to change, symbols, data flow, edge cases, tests, and verification commands. Do not edit files until approved.
03

IMPLEMENT — Kerjakan Slice Terukur

Minta Claude mengubah hanya file yang diperlukan dalam langkah kecil yang mudah direview.

Implement step [N] of the approved plan. Change only the necessary files in scope. Reuse canonical abstractions, write clean single-purpose functions, and pause after this slice for review.
04

VERIFY — Periksa Hasil Nyata

Jalankan test, lint, typecheck, build, atau /run lalu /verify bila aplikasi perlu diperiksa langsung.

Run relevant tests, linter, typecheck, and build commands. Execute /run and /verify against acceptance criteria. Report exact command outputs, passing checks, and any residual risks.
05

SHIP — Siapkan Rilis & Commit

Review diff secara detail. Commit, push, atau buat PR hanya setelah mendapat persetujuan eksplisit.

/code-review the current diff. Check for bugs, secret leaks, performance, and scope creep. If clean, propose a conventional commit message (type(scope): description) with evidence summary.

02 · Superpowers — Urutan Pemakaian

Plugin superpowers (v6.3.0) berisi skill proses yang wajib dicek Claude sebelum bertindak — bukan menu pilihan, tapi gate. Urutan di bawah adalah alur nyata dari yang paling awal (sebelum sentuh kode) sampai paling akhir (beres-beres branch).

1. brainstormingsebelum fitur baru

Wajib dipakai sebelum kerja kreatif apa pun — bikin fitur, komponen, atau ubah perilaku. Menggali intent, requirement, dan opsi desain sebelum plan mode dibuka.

Brainstorm this problem before coding. Identify constraints, unknowns, and 2–3 implementation options with trade-offs. Recommend one option, but do not edit files.
2. writing-plansspec sudah jelas

Begitu requirement dari brainstorming disepakati, ubah jadi rencana implementasi tertulis multi-step — sebelum file kode disentuh.

Write an implementation plan from the agreed spec. List files to change, exact symbols, edge cases, tests, and verification commands. Do not modify files until I approve the plan.
3. using-git-worktreeskerja butuh isolasi

Sebelum eksekusi plan atau mulai fitur berisiko, siapkan workspace terpisah (native tool atau git worktree) agar branch utama tidak ikut kotor kalau gagal.

Set up an isolated workspace for this task before starting — use a native isolation tool or a git worktree fallback. Confirm the workspace is separate from my current branch before making any changes.
4. test-driven-developmentsebelum tulis kode

Untuk setiap fitur atau bugfix, tulis test yang gagal dulu (red), baru implementasi (green). Ini gate wajib sebelum baris kode implementasi pertama ditulis.

Implement this using test-driven development. Write a failing test that captures the expected behavior first, show me it fails, then write the minimal code to make it pass. Do not write implementation code before the test exists.
5. systematic-debuggingada bug / test gagal

Dipakai begitu ada bug, test gagal, atau perilaku aneh — sebelum mengusulkan fix apa pun. Reproduksi dulu dengan test tersempit, baru telusuri akar masalah.

Investigate this bug: [BUG / ERROR]. Write or run the narrowest reproducing test to confirm the failure. Trace to root cause, propose minimal fix, and wait for approval.
6. dispatching-parallel-agentsriset banyak area

Ketika perlu menjelajah beberapa bagian repo yang independen sekaligus, sebar beberapa subagent paralel supaya context utama tetap bersih dari hasil eksplorasi mentah.

Dispatch parallel subagents to investigate these independent areas: [LIST AREAS]. Each subagent reports back a concise summary only — raw exploration output should not enter the main context. Do not edit files.
7. subagent-driven-developmenteksekusi plan di sesi ini

Untuk plan dengan task-task independen, delegasikan tiap task ke subagent dalam sesi yang sama, lalu review hasilnya satu per satu.

Execute the approved plan using subagent-driven development. Break independent tasks out to separate subagents in this session, review each result before moving to the next, and stop if scope expands beyond the plan.
8. executing-plansplan besar, sesi terpisah

Alternatif untuk plan besar: jalankan di sesi terpisah dengan checkpoint review manual di tiap tahap, bukan sekali jalan tanpa henti.

Execute this written plan in a fresh session. Pause at each major checkpoint for my review before continuing to the next step. Do not proceed past a checkpoint without explicit approval.
9. requesting-code-review + receiving-code-reviewselesai implement

Setelah slice implementasi selesai, minta review terstruktur, lalu proses feedback-nya secara sistematis — jangan langsung apply tanpa evaluasi tiap poin.

/code-review Review the current diff as a senior engineer. Return findings ordered by severity with file paths and line ranges. Do not rewrite code yet.
10. verification-before-completionsebelum bilang "selesai"

Gate terakhir sebelum task diklaim beres — paksa jalankan test/lint/build nyata dan cek terhadap acceptance criteria, bukan sekadar "kelihatan sudah benar".

Run relevant tests, linter, typecheck, and build commands. Execute /run and /verify against acceptance criteria. Report exact command outputs, passing checks, and any residual risks.
11. finishing-a-development-branchselesai, mau merge

Beres-beres branch di penghujung kerja — cek diff akhir, commit message, dan siapkan PR sebelum minta approval eksplisit untuk push.

This branch is ready to finish. Review the final diff end to end, confirm nothing unrelated is included, propose a conventional commit message, and prepare the PR description. Do not push or open the PR until I approve.
12. writing-skillsbikin skill baru

Kalau satu alur kerja terus berulang manual, tulis jadi skill baru di .claude/skills supaya bisa dipanggil ulang lewat Skill tool tanpa jelaskan ulang tiap sesi.

Write this recurring workflow as a reusable skill under .claude/skills. Include a clear description of when to trigger it, the exact steps, and any checklist items. Keep it self-contained so a future session can follow it without extra context.
Codex rescue subagentstuck / butuh second opinion

Plugin terpisah (codex) — dipakai saat Claude Code mentok, butuh implementasi kedua, atau investigasi akar masalah lebih dalam lewat runtime Codex.

Delegate this coding task to a Codex subagent: [DESCRIBE TASK]. Inspect relevant files first. Change only the approved scope, add focused tests, run relevant tests and lint, and report files changed, results, and risks. Do not commit, push, or create a pull request.

06 · Menjaga Performa Claude Code

Buat solo dev tanpa background coding: performa Claude Code turun bukan karena modelnya lemah, tapi karena context window kotor, CLAUDE.md kegemukan, atau task terlalu besar dijejalkan satu sesi. Ini checklist evidence-based dari setup akun ini sendiri.

1. Context window — resource paling berharga

Jangan biarkan satu sesi menumpuk log gagal & eksplorasi mentah. Pakai /clear tiap ganti task yang tidak berhubungan, dan /compact Focus on the current task kalau sesi mulai panjang tapi task masih sama.

2. Delegasikan eksplorasi, jangan baca semua sendiri

Untuk pencarian file/dependency yang open-ended, minta subagent ("gunakan subagent untuk investigasi X") atau fork — hasil investigasinya tidak ikut membebani context utama, cuma ringkasannya yang masuk.

3. CLAUDE.md tetap ramping

Taruh aturan build/test/lint & konvensi project di CLAUDE.md, tapi jaga di bawah ~100 baris. File yang gemuk dibaca ulang di setiap sesi dan makan context sebelum kerja dimulai.

4. Pilih model & effort sesuai bobot task

Task trivial (typo, rename mekanis) tidak perlu model/effort tertinggi. Task ambigu atau lintas-file baru layak dapat reasoning penuh + plan mode. /fast mempercepat output tanpa turun kelas model (Opus).

5. Kurangi interupsi permission prompt

Kalau sering diminta approve command read-only yang sama berulang, jalankan skill fewer-permission-prompts untuk scan transcript & tambah allowlist ke .claude/settings.json — bukan dengan mematikan semua permission check.

6. Audit plugin & hook yang aktif

Tiap plugin/hook aktif (caveman, vercel, sentry, dst) menambah instruksi yang dimuat tiap sesi. Copot yang sudah tidak dipakai lewat plugin manager supaya sesi tidak start dengan context yang sudah penuh instruksi tak relevan.

7. Evidence-based completion, bukan "kelihatan selesai"

Selalu jalankan lint → format → typecheck → test sungguhan dan tampilkan output-nya. Klaim "selesai" tanpa bukti command run adalah sumber bug yang lolos paling umum.

8. Memori lintas-sesi, bukan secret

Preferensi durable (cara kerja, keputusan project) boleh disimpan lewat sistem memory/hindsight MCP. Jangan pernah simpan API key, token, password, atau file .env/credential di mana pun yang bisa terbaca ulang otomatis.

9. Jangan bypass safety demi kecepatan

Hindari --no-verify, git push --force ke branch utama, atau rm -rf luas untuk "biar cepat selesai". Kalau hook/test gagal, itu sinyal untuk investigasi akar masalah — bukan alasan untuk skip.

# Rutin kebersihan sesi /clear # task baru, tak berhubungan /compact Focus on the current task # sesi panjang, task sama /cost # cek konsumsi token sesi aktif /doctor # cek instalasi & permission # Hindari (kecuali benar-benar perlu & sudah paham risikonya) git push --force git reset --hard rm -rf <path> --no-verify
