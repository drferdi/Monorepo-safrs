01 · Daily 5-Step Loop

Urutan Codex Agustus 2026 untuk setiap pekerjaan coding. Jangan minta Codex mengedit sebelum dia memahami repo, merencanakan tugas, dan punya kriteria “selesai” yang bisa dicek.

01

ORIENT — Pahami Project & Context

Buka repository yang benar. Baca AGENTS.md, HANDOFF, dan cek status Git tanpa mengedit file.

Orient yourself in this repository. Read AGENTS.md, relevant nested AGENTS.md, HANDOFF, project structure, and git status. Do not edit any files. Summarize architecture, canonical patterns, test commands, risk class (R0–R3), and key risks.
02

PLAN — Buat Rencana & Acceptance Criteria

Tekan Shift+Tab atau ketik /plan. Untuk perubahan multi-file atau berisiko, minta rencana dan review dulu — tidak ada file yang diedit selama Plan Mode aktif.

/plan Enter plan mode for [TASK]. Formulate a minimal implementation plan. List exact files to change, symbols, data flow, edge cases, tests, and verification commands. Do not edit files until approved.
03

IMPLEMENT — Kerjakan Slice Terukur

Minta Codex mengubah hanya file yang diperlukan dalam langkah kecil yang mudah direview. Isolasi dulu lewat worktree kalau kerjaan bisa mengotori checkout utama.

Implement step [N] of the approved plan. Change only the necessary files in scope. Reuse canonical abstractions, write clean single-purpose functions, and pause after this slice for review.
04

VERIFY — Periksa Hasil Nyata

Jalankan test, lint, typecheck, build, lalu /review dan /diff. Klaim “selesai” hanya kalau ada output command yang baru dijalankan.

Run relevant tests, linter, typecheck, and build commands. Use /diff and /review against acceptance criteria. Report exact command outputs, passing checks, and any residual risks.
05

SHIP — Siapkan Rilis & Commit

Review diff secara detail. Commit, push, atau buat PR hanya setelah mendapat persetujuan eksplisit.

/review the current diff. Check for bugs, secret leaks, performance, and scope creep. If clean, propose a conventional commit message (type(scope): description) with evidence summary. Do not commit, push, or open a PR until I approve.

02 · Superpowers — Urutan Pemakaian

Plugin superpowers (v6.2.0 di cache Codex Agustus 2026) berisi skill proses yang wajib dicek sebelum bertindak — bukan menu pilihan, tapi gate. Urutan di bawah adalah alur nyata dari yang paling awal (sebelum sentuh kode) sampai paling akhir (beres-beres branch).

0. using-superpowersawal percakapan

Gate sesi. Kalau ada 1% kemungkinan skill relevan, skill itu harus dibaca dulu sebelum jawab, tanya, atau eksplor. Proses dulu, implementasi belakangan.

Use using-superpowers first. Check which process skill applies before exploring or editing. Announce the skill you are using and follow it exactly.
1. brainstormingsebelum fitur baru

Wajib dipakai sebelum kerja kreatif apa pun — bikin fitur, komponen, atau ubah perilaku. Menggali intent, requirement, dan opsi desain sebelum Plan Mode dibuka.

Brainstorm this problem before coding. Identify constraints, unknowns, and 2–3 implementation options with trade-offs. Recommend one option, but do not edit files.
2. writing-plansspec sudah jelas

Begitu requirement dari brainstorming disepakati, ubah jadi rencana implementasi tertulis multi-step — sebelum file kode disentuh.

Write an implementation plan from the agreed spec. List files to change, exact symbols, edge cases, tests, and verification commands. Do not modify files until I approve the plan.
3. using-git-worktreeskerja butuh isolasi

Sebelum eksekusi plan atau mulai fitur berisiko, siapkan workspace terpisah (native worktree Codex atau git worktree) agar checkout utama tidak ikut kotor kalau gagal.

/worktree Set up an isolated workspace for this task before starting. Confirm the workspace is separate from my current branch before making any changes.
4. test-driven-developmentsebelum tulis kode

Untuk setiap fitur atau bugfix, tulis test yang gagal dulu (red), baru implementasi (green). Ini gate wajib sebelum baris kode implementasi pertama ditulis.

Implement this using test-driven development. Write a failing test that captures the expected behavior first, show me it fails, then write the minimal code to make it pass. Do not write implementation code before the test exists.
5. systematic-debuggingada bug / test gagal

Dipakai begitu ada bug, test gagal, atau perilaku aneh — sebelum mengusulkan fix apa pun. Reproduksi dulu dengan test tersempit, baru telusuri akar masalah.

Investigate this bug: [BUG / ERROR]. Write or run the narrowest reproducing test to confirm the failure. Trace to root cause, propose minimal fix, and wait for approval.
6. dispatching-parallel-agentsriset banyak area

Ketika perlu menjelajah beberapa bagian repo yang independen sekaligus, sebar beberapa subagent paralel supaya context utama tetap bersih dari hasil eksplorasi mentah. Butuh features.multi_agent = true.

Dispatch parallel subagents to investigate these independent areas: [LIST AREAS]. Each subagent reports back a concise summary only — raw exploration output should not enter the main context. Do not edit files.
7. subagent-driven-developmenteksekusi plan di sesi ini

Untuk plan dengan task-task independen, delegasikan tiap task ke subagent dalam sesi yang sama, lalu review hasilnya satu per satu. Juga butuh multi-agent.

Execute the approved plan using subagent-driven development. Break independent tasks out to separate subagents in this session, review each result before moving to the next, and stop if scope expands beyond the plan.
8. executing-plansplan besar, sesi terpisah

Alternatif untuk plan besar: jalankan di sesi terpisah dengan checkpoint review manual di tiap tahap, bukan sekali jalan tanpa henti.

Execute this written plan in a fresh session. Pause at each major checkpoint for my review before continuing to the next step. Do not proceed past a checkpoint without explicit approval.
9. requesting-code-review + receiving-code-reviewselesai implement

Setelah slice implementasi selesai, minta review terstruktur, lalu proses feedback-nya secara sistematis — jangan langsung apply tanpa evaluasi tiap poin.

/review Review the current diff as a senior engineer. Return findings ordered by severity with file paths and line ranges. Do not rewrite code yet.
10. verification-before-completionsebelum bilang "selesai"

Gate terakhir sebelum task diklaim beres — paksa jalankan test/lint/build nyata dan cek terhadap acceptance criteria, bukan sekadar “kelihatan sudah benar”.

Run relevant tests, linter, typecheck, and build commands. Use /diff and /review against acceptance criteria. Report exact command outputs, passing checks, and any residual risks.
11. finishing-a-development-branchselesai, mau merge

Beres-beres branch di penghujung kerja — cek diff akhir, commit message, dan siapkan PR sebelum minta approval eksplisit untuk push.

This branch is ready to finish. Review the final diff end to end, confirm nothing unrelated is included, propose a conventional commit message, and prepare the PR description. Do not push or open the PR until I approve.
12. writing-skillsbikin skill baru

Kalau satu alur kerja terus berulang manual, tulis jadi skill baru di ~/.agents/skills atau .agents/skills supaya sesi berikutnya tidak perlu dijelaskan ulang.

Write this recurring workflow as a reusable skill under ~/.agents/skills. Include a clear description of when to trigger it, the exact steps, and any checklist items. Keep it self-contained so a future session can follow it without extra context.

Master Agent Prompt Template

Bentuk resmi Agustus 2026: Goal / Context / Constraints / Done when. Jangan tumpuk aturan tahan lama di prompt — pindahkan ke AGENTS.md atau skill.

Goal: Selesaikan [TASK] di [PROJECT]. Context: Baca AGENTS.md, nested AGENTS.md, HANDOFF, pola canonical, dan error terkait. @ sebut file yang penting. Constraints: Perubahan minimal. Jangan sentuh secret, generated, atau file di luar scope. Hormati R0–R3. Done when: 1. [Hasil observable 1] 2. [Hasil observable 2] 3. Test/lint/typecheck yang relevan baru saja dijalankan dan outputnya dilampirkan. Workflow: inspect → /plan → implement slice → /diff + /review → verify. Guardrails: Berhenti jika scope melebar atau requirement ambigu. Jangan commit/push tanpa approval.

Guardrails untuk Codex

  • Satu chat = satu outcome. Ganti task yang tidak berhubungan? /new atau /clear.
  • Task sulit: /plan atau Shift+Tab dulu. Jangan langsung edit.
  • Kerja paralel di file yang sama? Isolasi dengan /worktree atau git worktree.
  • Review diff sebelum menerima perubahan. Jangan commit, push, atau delete tanpa approval.
  • Aturan tahan lama tinggal di AGENTS.md yang pendek, bukan di setiap prompt.
  • Multi-agent butuh features.multi_agent = true. Kalau flag itu belum ada, jangan pura-pura dispatch subagent.

06 · Menjaga Performa Codex

Checklist resmi Agustus 2026: Codex lemah bukan karena modelnya, tapi karena context kotor, AGENTS.md gemuk, satu chat dipakai untuk seluruh project, atau kerja hidup tanpa worktree.

1. Prompt = Goal / Context / Constraints / Done when

Empat field ini membuat Codex tetap scoped. Jangan tumpuk aturan tahan lama di prompt; pindahkan ke AGENTS.md atau skill.

2. Plan dulu untuk task sulit

Pakai /plan atau Shift+Tab. Atau minta Codex mewawancarai Chief dulu sampai ide kabur jadi konkret. Jangan skip planning di task multi-file.

3. AGENTS.md tetap ramping

Isi: layout repo, cara run/build/test, konvensi, do-not rules, arti “selesai”. Kalau gemuk, pecah ke file markdown spesifik dan tinggal di-referensikan. Nested AGENTS.md menang atas yang lebih umum.

4. Satu chat = satu outcome

Satu chat untuk seluruh project membuat context meledak. Tetap di chat yang sama hanya kalau masih satu masalah. Cabang sejati? /fork. Task baru? /new atau /clear.

5. Compact dan delegasikan eksplorasi

/compact untuk sesi panjang yang masih satu task. Subagent untuk riset bounded supaya log mentah tidak masuk context utama — hanya jika multi-agent aktif.

6. Worktree untuk kerja paralel

Kesalahan resmi: menjalankan beberapa task hidup di file yang sama tanpa Git worktree. Pakai /worktree atau worktree desktop + Handoff.

7. Reasoning sesuai bobot

Low untuk task sempit. Medium/High untuk perubahan kompleks atau debug. Extra High untuk kerja agentic panjang. /fast hanya jika model punya Fast tier.

8. Test + /review sebelum “selesai”

Minta Codex menulis tes bila perlu, jalankan check yang relevan, lalu /diff dan /review. Klaim selesai tanpa output command adalah bug yang paling sering lolos.

9. MCP dan skill hanya yang membuka loop nyata

Jangan pasang semua connector. Mulai dari satu-dua yang menghapus kerja manual berulang. Workflow yang sudah stabil baru dijadwalkan; yang masih perlu dikemudikan jadikan skill dulu.

10. Jangan bypass safety demi kecepatan

Jangan kasih full permission ke seluruh komputer sebelum workflow dipahami. Hindari git push --force ke branch utama, git reset --hard, dan hapus rekursif luas.
